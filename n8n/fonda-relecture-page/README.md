# Workflows n8n du parcours page — P3 (Emettre, Cloturer) et P2 (Page, Confirmer)

CDC relecture §21 (r10.9), découpage §21.9. Le **consommateur est gelé** depuis P1 (`fonda/scripts/rattachement-page.js`) : ces workflows **produisent exactement** ce qu'il attend (noms de nœuds, formes `cloture-fonda/v1` et `confirmation-fonda/v1`), sans redéfinir le contrat.

| Workflow | Déclencheur | Écrit | Observé par le signataire |
|---|---|---|---|
| `FONDA - Emettre relecture` | webhook POST, en-tête d'authentification, appelé par le CLI d'Éric | `relecture/<set_id>.candidat.json` (`candidat-fonda/v1`) ; courriel au relecteur | non (le candidat fait foi) |
| `FONDA - Cloturer relecture` | webhook POST, en-tête d'authentification, appelé par le CLI d'Éric | le même candidat, `statut: clos`, **premier** `clos_le` | **oui** : sortie `cloture-fonda/v1` |
| `FONDA - Page relecture` | webhook **GET** `/fonda-select?lot&k` (lien du courriel, public) | **rien** | non |
| `FONDA - Confirmer relecture` | webhook **POST** `/fonda-select-confirm` (navigateur du relecteur, public : protégé par `k` + jeton) | `decisions/<set_id>-<nonce>.json` | **oui** : sortie `confirmation-fonda/v1` |

- **Construction** : `construire-relecture.js --emettre | --cloturer | --page | --confirmer` produit les exports `box-fonda-<nom>-relecture.json`. Ne jamais éditer les nœuds dans l'interface ; jamais « Execute » ni « Retry » ; `retryOnFail` faux ; aucune donnée épinglée ; mode `webhook`.
- **Déploiement** : en P2/P3, **dépôt seulement**, rien sur l'instance. L'octet-identité est **interne** (export commité == construction depuis le dépôt, harnais `relecture.test.js`). L'octet-identité **dépôt ↔ live** (hors `updatedAt`, `versionId`, `versionCounter`) ne commence qu'à l'**import en P4** (recette sur copie, go d'Éric). Workflows créés **INACTIFS**, activés au plus tôt en P5.
- **Profil de recette (P4a)** : `--profil recette` construit les copies de test (`*.recette.json`) depuis `profil-recette.json` (identifiants seulement) ; la construction et le harnais (§1 bis) refusent tout identifiant de production, et les exports de production restent identiques octet pour octet. Protocole : `RECETTE-P4.md` ; outils en lecture seule : `outils-recette/`.
- **Valeurs de remplacement** (`A_RENSEIGNER_P4_…` dans `CONFIG`) : dossiers Drive `relecture/` et `decisions/`, chemins webhook du CLI, **ids** de credentials, id de la Data Table, URL de la page, base publique des fichiers moteur. Ce sont des identifiants, pas des secrets.
- **Secrets et données personnelles : jamais dans le dépôt.** Les credentials sont référencés par `{ id, name }` seulement (valeurs dans n8n). Le harnais **détecte des motifs connus** (adresse électronique, clé, jeton, littéral hexadécimal de 64 caractères, hors modules embarqués vérifiés comme copies exactes) : c'est un filet, pas une preuve d'absence.
- **Adresse du relecteur** : lue à l'exécution dans une **Data Table n8n** (clé = `relecteur_attribue`, identifiant non personnel déjà présent dans le candidat), absente de l'export. Elle transite par les données d'exécution au moment de l'envoi, comme `k` (§21.5, Emettre non observé). Lecture par le **nœud Data Table natif** (row/get, table par id, toutes les lignes, sortie toujours émise) : **aucune clé d'API n8n ni credential** (décision de l'architecte, 2026-11-10, réduction de surface) ; lue et **validée AVANT toute écriture du candidat** (nœud « Valider destinataire » : une seule ligne pour `relecteur_attribue`, une seule boîte en grammaire stricte bornée) ; table vide, relecteur absent ou en double, adresse hors grammaire -> erreur, **aucune écriture**, aucun courriel (en réémission, le candidat et l'ancien lien restent intacts). **Cas distinct** : Gmail en échec APRÈS l'écriture -> **envoi NON CONFIRMÉ, candidat déjà écrit ; réémettre** (le message a pu partir si la réponse s'est perdue ; jamais « aucun courriel », jamais de restauration de l'ancienne clé). La revalidation de l'adresse dans le courriel (point d'usage, `To:`) est une défense en profondeur : son mutant est équivalent par conception. Grammaire = robustesse (l'adresse vient de notre Data Table), pas une barrière anti-attaquant. Table **dédiée**, petite (2 lignes en recette), **non modifiée pendant une émission** (le nœud lit toutes les lignes ; n8n ne garantit pas un instantané pendant la pagination).
- **Clé `k`** : nœud Crypto v1 « Generate », 32 octets (hex 64). Seul `cle_sha256` = SHA-256 de l'UTF-8 de `k` est stocké ; `k` ne sort que vers le courriel (lien `…?lot=<set_id>&k=<k>`), jamais dans le candidat ni dans la sortie du workflow.
- **Émission** (pré-conditions §21.5 vérifiées **par le workflow**) : référentiel **archivé** au `journal_commit` consigné (SHA-256 des octets = `referentiel_version` annoncée) ; moteur au registre du même commit ; **réservation au journal** du même commit (ligne `reserve` et dernière transition `reserve`) ; lot source **complet** (`validerLot` embarqué, copie exacte de `catalogue.js` ; lot sans cartes refusé ; `set_id`, notion et palier cohérents) ; `relecteur_attribue` = relecteur de la notion du lot au référentiel archivé ; `expire_le` = maintenant + 14 jours. **Reste à la charge du CLI d'Éric** : la correspondance avec l'exécution de génération **retenue** (diagnostic « généré » avant l'appel) ; le workflow ne lit pas l'API des exécutions.
- **Réémission** (même workflow, même appel) : seulement si le candidat existe **une fois**, hors corbeille, au statut `en_attente` (`clos_le` null), **enveloppe entière valide** (forme exacte, dates ISO, chaque envoi, `generation_cle + 1` entier sûr), même lot (**`empreinte_complete`**, §21.5) et même provenance (relecteur, référentiel, moteur), **et** si `decisions/` du lot est **prouvé vide** : listing paginé complet, corbeille comprise, ni `incompleteSearch`, ni plafond de 50 pages atteint. Sinon **refus**, jamais de nouvelle `k` sur un état non prouvé vide. Effet : nouvelle `k` (nouveau `cle_sha256`), `generation_cle + 1`, `expire_le` = réémission + 14 jours (borné, non cumulé), `cree_le` inchangé, fichier **réécrit en place** (même identifiant Drive). L'ancien lien devient inactif (clé révoquée, R6).
- **`envois`** consigne chaque **tentative** : l'entrée est écrite dans le candidat **avant** l'envoi du courriel. C'est un **audit au mieux** (non signé) : une entrée perdue lors d'une course est une incomplétude d'audit, pas une brèche.
- **Courses (deux écrivains)** : Emettre (réémission) et Cloturer relèvent la **version Drive** du candidat **avant** d'en lire le contenu et la revérifient **juste avant** de réécrire ; écart = erreur, rien réécrit (Cloturer : E4, abandon au signataire ; Emettre : aucun courriel). Après l'écriture, la version renvoyée doit valoir **avant + 1** (comparée en `BigInt`) : détection **au mieux**, la sémantique d'incrément de Drive restant à vérifier en P4. Emettre **reliste** aussi `decisions/` après écriture (doit rester prouvé vide). Drive n'offre pas d'écriture conditionnelle fiable : la fenêtre résiduelle est fermée par le verrou mono-écrivain du CLI (ci-dessous).
- **Panne de courriel** : l'exécution d'émission échoue après l'écriture du candidat (tentative consignée). Une erreur d'envoi ne prouve **pas** que le courriel n'est pas parti : on ne déduit jamais la non-livraison de l'erreur. Relancer le même appel CLI ne prend le chemin **réémission** (génération de clé suivante) que si `decisions/` du lot est **prouvé vide** ; sinon Emettre refuse (« ni émission ni réémission ») et le lot suit le chemin d'abandon (nouveau `set_id`, §21.5).
- **Page** (§21.6, aucune écriture) : C3 au GET (candidat unique hors corbeille, `en_attente`, `cle_sha256` = SHA-256 de `k`, non expiré, lot conforme, moteur **au registre**) ; sinon page « indisponible » **sans aucune donnée du lot** (400 requête mal formée, 410 sinon). Deux aléas **distincts** par affichage (Crypto v1, 128 bits) : `csp_nonce` (CSP, jamais posté) et `nonce` (formulaire). `expire_page` = affichage + 60 min, borné par `expire_le`. CSP **en `<meta>`** exacte du §21.6, `referrer` `no-referrer`. Moteur chargé depuis son **URL exacte** avec **SRI sha384 calculée à la construction** depuis le fichier du registre (sha256 du fichier = registre, sinon la construction échoue). Données dans `<script type="application/json">` échappé ; script sous nonce, `textContent` seulement ; aucun gestionnaire inline ; **aucun `<form>` dans le HTML** (le script le construit à l'envoi) ; sans JavaScript : « page de relecture indisponible sans JavaScript ». UX : une carte à la fois, Garder/Écarter désactivés jusqu'au rendu, aucun choix par défaut, retour possible, récapitulatif seul point d'envoi, « Tout rejeter » séparé et confirmé. `k` ne figure dans la page qu'en champ du formulaire posté.
- **Confirmer** (C1–C7, §7, §21.1) : C1 avant Drive (taille ≤ 64 Ko : `content-length` **et** somme des champs ; champs **exacts** ; doublon = tableau -> refus) ; **C2 = authenticité** (jeton recalculé sur les valeurs **postées**) ; **C3 = fraîcheur** contre le candidat **courant** (statut, `cle_sha256`, génération, `expire_le`, `expire_page`, moteur ; 410) ; C4 empreinte affichée = actuelle ; C5 un choix par carte ; C6 même nom (corbeille comprise, recherche **paginée**) : cœur identique -> `existante` (décision **relue**), sinon `conflit` (409) ; C5bis candidat **relu** juste avant l'écriture. **C7 (courriel) retiré** : une exécution observée ne contient aucun effet de bord au mieux (son statut porte l'intégrité) ; notification par le CLI de clôture ou un workflow séparé non observé (P5). Encodage **imposé** : `application/x-www-form-urlencoded` (sinon C1). **Limite** : deux resoumissions identiques **simultanées** peuvent créer deux fichiers (Drive sans écriture conditionnelle) -> abandon R3 au signataire : disponibilité, pas intégrité. Tout rejet = exécution `success`, rien écrit ; une panne = erreur d'exécution (E4 : abandon si le lot est lisible). `executionTimeout` 120 s.
- **Secret HMAC (P4b, option E)** : calculé par un nœud **Crypto v1 « hmac »** (SHA256, hex) — « Signer jeton » (Page), « Recalculer jeton » (Confirmer) — sur la **chaîne** canonique (`messageJeton`, octets identiques à `tableauCanonique` ; vecteurs inchangés). Dans le dépôt, paramètre `secret` = valeur de remplacement `A_INJECTER_A_L_IMPORT` (fragment unique) ; le secret d'instance est substitué dans le TEXTE du JSON par `outils-import/importer-recette.js` (trousseau macOS, POST inactif). Secret non injecté = HMAC de la valeur publique -> **erreur** (garde dans « Construire page » et « Verifier formulaire »), jamais une page ni un C2 accepté. La **forme** du secret (64 hex) est garantie par l'outil d'import et par comparer-live, **pas** par le workflow (le nœud ne peut pas lire son paramètre sans l'exposer) ; son caractère aléatoire tient à sa génération (`openssl rand -hex 32`). Les rejets C1 et la page « indisponible » **contournent** Crypto (nœuds IF « Syntaxe valide ? », « Page disponible ? ») : une panne de Crypto ne transforme jamais un rejet en erreur ; sorties de rejet identiques à l'avant-P4b (différentiel du harnais). Plus aucun `$env` (bloqué par défaut en n8n 2.x). **Critère révisé** : « Le secret HMAC du jeton de page est un secret d'INSTANCE : absent du dépôt public et de la page, inatteignable par le relecteur et le public. Il est présent en clair dans la base n8n, l'historique des versions, les réponses de l'API et les instantanés workflowData d'exécution (permanents, purge désactivée), accessible aux seuls détenteurs d'un accès instance ou clé API (l'opérateur de confiance) et transite vers le Mac d'Éric via includeData. Sa compromission affaiblit le filtre C2 mais ne forge aucune attestation signée : l'intégrité probante reste la signature humaine. La rotation invalide les pages déjà ouvertes et n'efface pas les copies antérieures. Accepté car Crypto v2/credential est indisponible en n8n 2.6.3, l'objectif (le relecteur ne peut forger le jeton) est atteint, et les alternatives (montée de version, refonte C2/CDC) sont disproportionnées. Migration future possible vers un credential Crypto v2 chiffré si l'instance est mise à niveau. »
- **Profils** affichés par la page : explications **par version du moteur** (v1 : CDC §4.3, le singulier/pluriel n'est **pas** pardonné en `sens`, écart documenté au PRD §5.1), chaque exemple vérifié par ce moteur dans le harnais ; une version sans explications fait échouer la construction.
- **Points P4 (Page, Confirmer)** : code HTTP du Respond to Webhook par expression ; en-têtes `content-type` et `content-length` présents dans l'item du webhook ; forme des doublons livrée par n8n (tableau attendu) ; URL publique des moteurs (CORS) ; Crypto v1 « Generate » hex 32.
- **Recherches par nom exact paginées** (défaut P3 corrigé en P2) : lot source et candidat existant (Emettre), candidat (Cloturer, Confirmer, Page) suivent les jetons de page (une page vide portant un jeton est normale chez Drive) ; comptage inchangé (exactement un fichier, ou 0/1 selon le cas), incomplétude ou plafond = erreur.
- **Point P4** : `name contains` de Drive fait une correspondance par préfixe de mots ; la recherche des décisions double donc le nom par la propriété `fonda_set_id`. Comportement exact à vérifier sur la copie.
- **Clôture** : `en_attente` → `clos` avec le **premier** `clos_le` ; déjà `clos` → `deja_clos: true`, rien réécrit (le nœud d'écriture ne s'exécute pas) ; tout autre statut (dont `abandonne`) → erreur. L'entrée `FONDA Entree cloture` ne fait que copier `set_id` (chaîne ≤ 128, sinon `null`) et ne lève jamais (§21.1). `clos_le` d'un candidat déjà clos est **validé** (ISO canonique) avant toute sortie réussie, jamais réécrit. `nb_decisions_listees` et `incomplete_search` portent sur tout `decisions/` du lot, corbeille comprise ; `incomplete_search` = OU des `incompleteSearch` Drive **seulement** (§21.1) ; plafond de pagination atteint (50 pages ; `pageSize` 1000 est un maximum, Drive peut rendre moins) = **erreur d'exécution**, aucune sortie (E4, abandon au signataire).

## Où vit chaque garantie

| Garantie | Où | Mécanisme |
|---|---|---|
| Correspondance génération ↔ candidat (moteur, `referentiel_version`, `empreinte_complete`, relecteur) | **signataire** | `evaluerPage` compare le candidat à la génération **retenue** : abandon si écart. Emettre ne vérifie que sa cohérence interne (référentiel et moteur au commit, réservation sans `ref`) ; le diagnostic « généré » du CLI est un confort, pas une garantie |
| Décision conforme au lot relu (empreintes pédagogiques, sélection, lot filtré) | **signataire** | réconciliation §20.5 (`L.reconcilier`, `L.unicite`) |
| Clôture irréversible, liée au candidat lu | **signataire** | E12 (`candidat_fichier_id`, `clos_le`), cohérence **mutuelle** des clôtures (dates différentes -> abandon) |
| Clé révoquée à la réémission | **signataire** (pilier 1) | R6 (`generation` exécution = fichier = `generation_cle`) ; ferme ce que le relecteur peut provoquer seul (ancien lien). R6 ne vaut que si aucune génération n'est **réutilisée ni rétablie** : c'est le pilier 2 |
| Un seul écrivain CLI à la fois (émission, réémission, clôture jamais en parallèle) | **CLI (P5)**, pilier 2, **contrôle d'intégrité** | verrou local + refus de lancer si une exécution Emettre/Cloturer est en cours (API n8n) : **prévention**, seul mécanisme d'intégrité de la classe « deux écrivains » (D1, D2, E1). P5 ne peut pas être livré sans lui. **Critère de livraison P5** : CLI lancé depuis le **seul Mac d'Éric** (verrou local + listing n8n n'excluent pas deux hôtes, qui peuvent voir zéro exécution et démarrer ensemble ; multi-hôte = exclusion partagée, à arbitrer en P5) |
| Écriture d'un état périmé | Emettre **et** Cloturer | version Drive relevée avant lecture, revérifiée avant écriture ; version après = avant + 1 (au mieux, à vérifier en P4) : **signal précoce** d'une violation du pilier 2, **pas** un mécanisme d'intégrité (E1 : l'écriture atterrit avant l'erreur, et une erreur d'Emettre après écriture n'annule pas cette écriture) |
| Traçabilité des envois | candidat (`envois`) | **audit au mieux**, non signé |
| Formulaire authentique / à jour | Confirmer (C2 / C3, C5bis) | C2 : jeton HMAC sur les valeurs postées (forgé -> 403) ; C3 : candidat courant (révoqué, remplacé, expiré -> 410), avant toute écriture. Fermeture **précoce** : le signataire (R6, réconciliation, unicité) reste l'intégrité |
| `hash_formulaire` | décision (`decision-fonda/v1`) | **audit rapproché, non signé** : empreinte canonique du formulaire posté (tableau à schéma validé, §21.1), calculée par Confirmer, couverte par `decision_sha256` (R1) **avant** signature, **absente de l'instantané v1** signé ; vérifiée par le harnais seul, sans re-dérivation aval. Aucune garantie : l'intégrité est cœur + `lot_relu` (signés, §20.5, unicité) |
| Statut des exécutions observées (Confirmer, Cloturer) | workflows | **porteur d'intégrité** (E4 abandonne tout non-`success`) : travail essentiel déterministe **seulement**, aucun effet de bord au mieux (courriel, journal externe), rien après la réponse ; vérifié statiquement par le harnais |

L'intégrité repose sur **deux piliers** :

- **Pilier 1, le signataire** (inconditionnel) : ferme tout ce que le **relecteur**, non fiable, peut provoquer seul : correspondance à la génération retenue, réconciliation §20.5 et unicité, E12, cohérence mutuelle des clôtures, R6.
- **Pilier 2, le verrou « un seul écrivain CLI à la fois »** (§21.5, livré en P5), **porteur** : ferme tout ce qui exige **deux écrivains CLI en parallèle**, c'est-à-dire une erreur de l'**opérateur**. C'est un **contrôle d'intégrité**, pas un confort : P5 ne peut pas être livré sans lui, et le verrou sera relu au niveau du signataire à sa livraison. Cette classe compte trois entrelacements connus. Le **signataire seul** est trompé par les trois (`constats: []`, montré par la relecture de 57ffde5) ; la **chaîne actuelle** (signataire + contrôles de version) rattrape certains ordonnancements (D1 : abandon ; D2 : refus de l'écriture périmée), mais **pas E1** :
  - **D1** : une clôture partie de la génération 1 écrase une réémission en génération 2 (clé révoquée rétablie, confirmation de génération 1 acceptée) ;
  - **D2** : deux réémissions concurrentes écrivent toutes deux la génération 2 ;
  - **E1** : la réémission A franchit son contrôle de version, B écrit la génération 2 et envoie sa clé, une confirmation passe sous la clé de B, puis A écrase la clé de B (toujours génération 2) et échoue **après** son écriture. La décision est acceptée sous une clé qui n'est plus celle du candidat, même avec un incrément de version exact. **Fermé par le verrou P5 seulement.**

Les contrôles de version d'Emettre et de Cloturer **détectent** les modifications visibles au moment du contrôle et font surfacer tôt ces violations (le harnais, section 9, montre Cloturer en erreur sur D1 et la réémission périmée refusée sur D2) ; ils n'excluent pas les écritures concurrentes postérieures au contrôle (E1). Ajouter au signataire une comparaison des clés dégèlerait P1 et échouerait sur D1 (la restauration périmée rend les clés de nouveau égales). Avec un seul écrivain, les autres entrelacements (réémission effaçant `clos_le`, confirmation par l'ancien lien) finissent en refus ou abandon à la signature.

**Seuil de remise en cause** : si une relecture trouve encore un entrelacement que ces deux piliers ne ferment pas, on ne rapièce pas ; on reconsidère le modèle d'écriture du candidat (versionné par génération ou en ajout seul, au lieu de la réécriture en place).

- **Harnais** (`relecture.test.js`) : **faux Drive fidèle** (requête `q` interprétée clause par clause, `fields` projetés, pagination par jeton ; une clause non simulée fait échouer le test) partagé par les producteurs n8n **et** le signataire (vrai `adaptateurs-page.lecturePage`) ; transport de la pagination reconstitué selon la configuration du nœud (jeton en query string) ; chaîne **réelle** Emettre → **vraie Page** → **vrai Confirmer** → Cloturer → vrais `preLireDetails`, `rattacherPage`, `evaluerPage` **et réconciliation §20.5**, avec les **vraies preuves** de génération (empreinte complète, `referentiel_version`, moteur, relecteur) et leurs contre-épreuves ; verrou E12, cas du §21.10, réémission, C1–C7, R3, 409, multi-nonce. La confirmation **au contrat** ne subsiste que pour les contre-épreuves de réconciliation (décision fausse mais cohérente). Adaptations au simulateur (non modifiable), dans la copie de test seulement : nœuds Crypto -> valeurs fixes ; requête GET injectée devant « Lire requete » ; Respond to Webhook (corps texte, code par expression évalué par le harnais) — chaque forme d'origine vérifiée statiquement. Le **script de la page est exécuté** dans un DOM minimal (`vm`, sans dépendance ; `innerHTML`, `outerHTML`, `insertAdjacentHTML` et `document.write` y **lèvent**) : **soumission simulée** — les occurrences réellement soumises sont sérialisées en URL-encodé, décodées en **conservant les doublons**, puis postées au vrai Confirmer ; le transport navigateur → webhook est une recette P4. Vérification complémentaire ponctuelle en navigateur réel (Playwright, hors CI) : CSP sans violation, SRI acceptée.
