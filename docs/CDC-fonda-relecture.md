## 0. Garantie, filet, limites

**Garantie (humaine, vérifiable par une signature)** : un lot n'est publiable que si la relectrice a confirmé auprès d'Éric **exactement l'instantané figé** (§3) — cartes gardées et écartées, règle de correction, **moteur de correction élève** (version + empreinte) que l'élève exécutera (§4) — et si Éric a signé cet instantané sur son Mac. **Confirmation, signature et comportement exécuté par l'élève forment un seul objet lié** (§3, §4, §11).

**Filet technique** (exécutions n8n, rapprochement historique/Drive, recherches Drive, conflits, empreintes, SRI) : il **bloque** ce qu'il détecte (§10). **Il est non probant.**

> **Limite, noir sur blanc.** Drive + n8n 2.6.3 n'offrent ni écriture atomique, ni journal infalsifiable, ni rétention garantie, ni état d'exécution exhaustivement interrogeable. **Le silence du filet ne prouve pas l'exhaustivité.** FONDA ne revendique **aucune** preuve technique d'exhaustivité ni d'unicité : l'unicité de ce qui est publié repose sur la **confirmation humaine** de l'instantané exact.

**Ce que prouve la signature** : la **déclaration d'Éric** (« la relectrice `<id>` m'a confirmé, par `<mode>`, cet instantané exact, transmis sans retouche ; je l'ai signé »). Pas l'intervention indépendante de la relectrice, ni son examen réel de chaque carte.

**Non couvert, assumé** : administrateur n8n/Drive/GitHub malveillant ; relectrice confirmant sans examiner ; Éric déclarant faussement (racine de confiance).

**Périmètre** : `fonda/page/bootstrap.js` et `fonda/engine/carte-reponse-produite.js` ne servent **qu'au mode FONDA** (`?fonda=1`), **pas encore sur `main`** ; BOX (élèves actuels) n'en dépend pas. **Frontière CI** : vérification publique uniquement ; jamais la clé privée RSA ni le jeton n8n. **Le front ne vérifie pas RSA** : il sert le catalogue mergé, et vérifie l'empreinte du lot et la **SRI du moteur** qu'il charge (§4).

## 3. Instantané figé et confirmation humaine (B1 v4, C3)

1. **Instantané** `instantane-fonda/v1 = { schema, set_id, candidat_lot, coeur, lot_relu, moteur: { version, sha256 }, recapitulatif }` ; `recapitulatif` = **projection déterministe** de `candidat_lot` + `coeur` + `moteur` (cartes gardées/écartées, règle de correction de chaque carte gardée, version du moteur, empreintes). `sha256_instantane` = SHA-256 complet ; **code de confirmation** = 16 premiers hex (repère humain seulement).
2. **Enregistrement unique** au moment de la construction : `instantane.json` + `export.json = { sha256_instantane, sha256_recapitulatif, exporte_le }` dans le dossier local de clôture (hors dépôt, hors Dropbox). Affichage, export et signature dérivent de cet instantané ; il n'est **jamais reconstruit**.
3. **Transmission sans retouche** : export en fichier joint `recapitulatif-<set_id>-<code>.txt` (récapitulatif + `sha256_instantane` en dernière ligne), envoyé tel quel ; la relectrice **répond à ce message** en citant le code. Vive voix : lecture commune de l'affichage du script.
4. **Contrôles obligatoires avant signature** (C3) : (a) SHA-256 recalculé de `instantane.json` = `export.json.sha256_instantane` ; (b) `recapitulatif` = projection déterministe recalculée de l'instantané, et son SHA-256 = `export.json.sha256_recapitulatif` ; (c) `coeur`, `moteur` et empreintes de la charge **proviennent exclusivement** de l'instantané ; (d) Éric tape le code confirmé (= code de l'instantané) et atteste la fidélité de transmission. Le code n'authentifie ni personne ni message.
5. **Clôture technique ≠ clôture signée** : la *clôture technique* (révocation de la clé, §9) précède la confirmation ; **sans confirmation, pas de clôture signée** et donc rien de publiable.

## 4. Moteur de correction élève versionné (B1, B2 v5 ; B1, C1, C3 v6)

**Principe** : **toute décision pédagogique observable** par l'élève est prise **par le moteur** ; le composant d'affichage et le front ne font **qu'afficher** ce que le moteur renvoie. Aujourd'hui ces décisions sont éparpillées (`correction.js`, `adapterCarte`, `carte-reponse-produite.js` : cible affichée, verdict, icône, formes affichées, seconde chance, tentative comptée, verrouillage ; `bootstrap.js` : apparition de « Carte suivante »).

### 4.1 Mécanisme d'export (fixé, testé par la preuve C8)

Fichier `fonda/engine/moteur-correction-v<N>.js`, chargé par balise `<script>` avec `integrity` et `crossorigin="anonymous"` posés **avant insertion**. Son **seul** effet de bord est l'enregistrement **sous sa version** dans un registre **global lui-même non réassignable** :
```js
var d = Object.getOwnPropertyDescriptor(self, "FondaMoteurs");
if (!d) Object.defineProperty(self, "FondaMoteurs", { value: Object.create(null), writable: false, configurable: false, enumerable: false });
else if (d.writable || d.configurable || Object.getPrototypeOf(d.value) !== null) throw new Error("registre FondaMoteurs incompatible");
var R = self.FondaMoteurs;
if (!Object.prototype.hasOwnProperty.call(R, "v<N>"))
  Object.defineProperty(R, "v<N>", { value: Object.freeze({ version: "v<N>", creerMoteur }), writable: false, configurable: false, enumerable: true });
```
- **Ni le registre ni une version ne peuvent être remplacés** : la propriété globale `FondaMoteurs` est non réassignable et non configurable (le registre reste **extensible** pour accueillir de nouvelles versions) ; un registre préexistant incompatible (réassignable, configurable ou à prototype) → **refus** ; une version enregistrée n'est ni remplacée ni modifiable. Aucun autre global n'est posé.
- **Origine connue** : la présence d'une version dans le registre **ne suffit pas** ; le chargeur conserve sa propre table `version:sha256 → chargée sous cette SRI`. Une version présente dans le registre sans avoir été chargée par lui sous la SRI demandée → refus.
- **Chargeur** (front et page de relecture) : `obtenirMoteur(version, sha256)` — **d'abord**, et **avant tout chargement**, contrôle de concordance : `moteurs.json[version].sha256 === sha256` (sinon refus immédiat ; une même version ne peut pas correspondre à deux empreintes). Ce contrôle est fait **pour chaque demande, y compris deux premières demandes simultanées** portant des empreintes différentes (l'une est refusée avant toute balise). Puis cache **indexé sur `version + ":" + sha256`**, une seule promesse partagée par clé ; chargement du fichier avec la SRI encodant **ce** `sha256` ; lecture de `FondaMoteurs[version]` ; `instance = fabrique.creerMoteur()` ; `instance.version === version` exigé. **Échec de chargement** : la promesse est oubliée, une nouvelle tentative recharge (nouvelle balise).
- **Tests** : séquence v1 → v2 → v1 (comportements **différents**) ; deux chargements concurrents de même clé (une balise) ; deux premières demandes simultanées d'empreintes différentes (une refusée, aucune balise pour elle) ; **réassignation du registre entier** (`self.FondaMoteurs = {}` et `defineProperty`) sans effet ; écrasement d'une version sans effet ; registre préexistant incompatible → refus ; échec de chargement puis nouvelle tentative ; deux instances distinctes issues d'une fabrique chargée une seule fois. *(Preuve C8, 2026-10-13 : mécanisme validé en navigateur réel sur l'instance, hors la réassignation du registre entier, ajoutée par la v8.)*

### 4.2 API du moteur : un résultat pédagogique complet

`creerMoteur()` renvoie `{ version, valider, preparerCarte, demarrer, soumettre }`, **purs** (aucun DOM, aucun réseau) :
- `valider(carteLot) → { valide, issue_si_invalide, raisons }` : **toutes** les validations dépendant du profil et de l'arrondi (profils connus, bornes d'arrondi, cohérence des réponses acceptées, formes saisissables) sont **dans le moteur** ; le front, le générateur, la publication et la CI les appellent **sur le moteur du lot** (§4.3). Les contrôles de transport, d'empreinte et de structure publique (`lot-fonda/v1`) restent hors moteur.
- `preparerCarte(carteLot) → carte` : données d'affichage **préparées**, dont `cible_affichee` (ex. `0,33` pour `1/3` avec arrondi 2) — **préparer n'est pas afficher** : la cible n'est **montrée qu'après soumission**, dans le feedback, comme aujourd'hui.
- `demarrer(carte) → etat` ; `soumettre(etat, saisie) → { etat, resultat }`.
- **API de validation pour l'outillage** (générateur, publication, CI) : `outils = { verifierReponseOr(carte), verifierFormesAcceptees(carte), formeSaisissable(carte, forme) }`, exposée par le **même fichier versionné** ; **`verifierReponseOr` reprend exactement la sémantique de l'actuel `verifierContreCorrecteur`** (réponse-or testée littéralement, statut `juste` exigé), `verifierFormesAcceptees` et `formeSaisissable` celles du même nom dans `generer-lot-fonda.js` ; aucun parseur ni normaliseur parallèle hors moteur.

`resultat` est **complet et définitif** pour l'affichage :
`{ issue ∈ {"juste","presque","faux","carte_invalide","erreur"}, reussite, verdict: { texte, icone ∈ {"succes","echec","alerte"} }, cible_affichee, formes_affichees, profil_libelle, afficher_badge_relecture (booléen), tentative (1|2), compte (booléen), seconde_chance_ouverte, verrouillee, carte_terminee }`.

**Table des issues et règle de comptage (sémantique actuelle préservée exactement)** :

| Issue | Origine | `reussite` | `compte` (tentative scorée) | Verrou / fin | Badge de relecture |
|---|---|---|---|---|---|
| `juste` | évaluation | true | true en 1re tentative | verrouillée, terminée | affiché |
| `presque` | évaluation | selon profil (true en `sens`/`numerique`, false en `orthographe`) | true en 1re tentative ; **jamais** en 2e | seconde chance ouverte si prévue, sinon verrouillée et terminée | affiché |
| `faux` | évaluation | false | true en 1re tentative | verrouillée, terminée | affiché |
| `carte_invalide` | la carte est incohérente (ex. réponse acceptée non conforme à son profil) | false | **true** (comme aujourd'hui : un échec compté) | verrouillée, terminée | **masqué** (on n'affirme pas « relue et validée » sur une carte invalide) |
| `erreur` | exception technique pendant l'évaluation | false | **false** (rien n'est scoré, comme aujourd'hui) | verrouillée, terminée (l'élève peut avancer) | masqué |

**Correspondance exacte avec le correcteur actuel** (aucune règle nouvelle) : **profil inconnu → `faux`** (pas `carte_invalide`) ; **arrondi invalide → comparaison exacte** (l'arrondi est ignoré, pas d'invalidité) ; `carte_invalide` = **uniquement** le cas où le correcteur actuel le renvoie (attendu incohérent : fraction ratée, reliquat non conforme, unité contradictoire). `valider` signale ces situations pour l'outillage mais **ne change pas l'issue élève** qui en découle aujourd'hui.

Aucune fusion silencieuse entre `carte_invalide` et `erreur`. *(Question ouverte pour Éric : conserver « carte invalide = échec compté de l'élève » ? Par défaut : **inchangé**.)* `onErreur` disparaît : l'issue `erreur` passe par le même canal que les autres.
- La **normalisation** des saisies, le **parseur numérique**, la cible, les formes affichables, la règle « presque compte / ne compte pas » selon le profil, la seconde chance et le verrouillage sont **dans le moteur** ; aucun prétraitement dans l'interface.
- **Composant** `carte-reponse-produite.js` : purement présentationnel ; reçoit `{ moteur, carte, onResultat }`, affiche `carte` puis `resultat` **sans réinterpréter** (aucun `if` sur le statut ou le profil autre que le choix de gabarit d'affichage dicté par `resultat`).
- **Navigation** : « Carte suivante » n'apparaît que si `resultat.carte_terminee === true` (corrige le défaut actuel : elle apparaît dès le premier résultat alors qu'une seconde chance reste ouverte).
- **Contrat `onResultat`** : appelé **une fois par soumission**, **après** mise à jour de l'affichage et du verrouillage, avec `resultat` **tel quel** (objet gelé) ; une exception dans `onResultat` est **interceptée et journalisée** sans modifier l'affichage, le verrouillage ni l'état du moteur.
- **Inventaire des écarts volontaires** par rapport au comportement actuel (tout le reste est identique et prouvé par les tests rejoués) : (E1) **navigation** — « Carte suivante » n'apparaît que si `carte_terminee` (aujourd'hui dès le premier résultat) ; (E2) **ordre d'appel** — `onResultat` appelé **après** le verrouillage (aujourd'hui avant) ; (E3) **exception de callback** — interceptée (aujourd'hui elle remonte) ; (E4) **canal d'erreur** — issue `erreur` dans `resultat` au lieu d'`onErreur`. Les tests actuels qui exigent l'ancien ordre, la remontée d'exception ou `onErreur` (`carte-reponse-produite.test.js`, `bootstrap.test.js`) sont **révisés explicitement** et listés dans la PR ; les autres tests sont **adaptés à la nouvelle interface** (moteur injecté, `resultat` au lieu des arguments actuels) **sans changer aucune attente pédagogique** (issue, réussite, comptage, cible, formes affichées, seconde chance). Toute modification d'une attente pédagogique hors E1–E4 est interdite.
- **Ordre des cartes** : celui du tableau du lot (couvert par l'empreinte) ; le front **ne trie jamais** (ni par `numero`, ni autrement).
- **Émetteur d'événements** (futur, T3/T5) : transmet `resultat.compte`, `resultat.reussite` et `resultat.issue` **tels quels**, sans recalcul ; n'émet que si `compte === true`.

### 4.3 Registre, liaison, version figée

- **Registre** `fonda/engine/moteurs.json` = `[{ version, fichier, sha256, sri }]` ; invariant `sha256 = SHA-256(octets du fichier)` et `sri = "sha256-" + base64(même empreinte)`. Fichiers **immuables, jamais supprimés** (annexe B).
- **Liaison** : `moteur = { version, sha256 }` fixé dans le candidat → page de relecture (« Essayer une réponse » via **le même** `obtenirMoteur`) → jeton HMAC et champ POST → cœur → instantané → charge signée → entrée du catalogue.
- **Front élève** : résoudre l'entrée **avant** tout chargement ; `obtenirMoteur(entree.moteur.version, entree.moteur.sha256)` ; échec → « pas disponible ».
- **Génération, publication, CI (C3)** : toutes les validations de cartes (`verifierContreCorrecteur`, `verifierFormesAcceptees`, `formeSaisissable`) passent par **le moteur du lot** (`moteurs.json` + fichier versionné, chargé en Node), **jamais** par le correcteur courant ; aucune logique numérique parallèle.
- **Version figée par lot publié** : `entree.moteur` est figé comme l'empreinte (annexe B) ; tout changement de comportement ⇒ nouveau `set_id` + nouvelle relecture.
- **Lots historiques et migration initiale (C6)** : `moteur-correction-v1.js` = consolidation **à comportement identique** du code actuel, **à l'exception des écarts volontaires E1–E4** (§4.2), qui ne changent ni l'évaluation ni le comptage. Preuve : tests existants rejoués + comparaisons ancien/nouveau (cible affichée, profils, Unicode, arrondi, seconde chance, callbacks). **Écart documenté** : le PRD §5.1 annonce une tolérance singulier/pluriel en profil `sens` que le normaliseur actuel ne réalise pas ; v1 **préserve** le comportement actuel. **Deux migrations nommées** : **M1 « moteur v1 »** (étape 2, §18) ajoute `moteur: { version: "v1", sha256 }` aux **8 lots historiques seulement**, avec le registre, le code du moteur et la forme du badge — **aucune mutation pédagogique** (empreintes inchangées) ; **M2 « journal des identifiants »** (étape 3) crée et amorce `set_ids-journal.json`. L'exception d'immuabilité de M1 est **consommable une seule fois** : elle n'est admise que si **aucune version** du catalogue de l'historique de confiance n'a jamais contenu de champ `moteur` (annexe B, règle 0) ; dès que M1 est fusionnée, elle ne peut plus se reproduire.

## 6. Clé, statuts, identifiants (C4 v4, C5)

- Clé : Crypto v1 « Generate », hex 64 ; seul `cle_sha256` stocké ; **14 jours**. Seuls les workflows **déclenchés manuellement par CLI** (webhook à authentification, §21.0 ; jamais « Execute » dans l'interface) écrivent le candidat (génération, réémission, clôture technique, abandon), jamais en parallèle.
- Contrôle C3 (§7) : candidat téléchargé par l'exécution : `statut === "en_attente"`, `sha256(k)`, génération, expiration, **`moteur` = celui du formulaire**.
- **Statuts** : `en_attente → clos` ; `en_attente → en_attente` (réémission) ; `en_attente | clos → abandonne`. Après un **blocage dur propre au lot** (§10), seule issue : **abandon** + **nouveau candidat** avec **nouveau `set_id`** (cartes reprises, `set_id` réécrit dans chaque carte, `item_id` conservés, empreintes recalculées, **relecture entièrement refaite**).
- **Journal des identifiants (C5 v5, C2 v6)** : fichier **commité** `fonda/data/set_ids-journal.json` = **journal de transitions en ajout seul** `[{ set_id, transition ∈ {"reserve","publie","abandonne","retire"}, le, ref }]`. L'état courant d'un `set_id` est **dérivé** de sa dernière transition (aucune ligne n'est jamais modifiée ni supprimée). Transitions autorisées : `reserve → publie`, `reserve → abandonne`, `publie → retire` ; jamais de nouvelle `reserve` pour un `set_id` déjà présent.
  - **Amorçage (M2)** : pour **chaque** `set_id` déjà utilisé (catalogue, `lots/`, `lots-fonda-calibration/`, historique Git de ces fichiers) : les 8 publiés → `reserve` + `publie` ; les 8 de calibration présents → `reserve` (promouvables) ; **tout identifiant ayant disparu de l'historique sans publication, ou dont l'histoire est indéterminée → `reserve` + `abandonne`** (jamais réutilisable, jamais promouvable).
  - **Autorité et sérialisation** : la branche **`design`** fait autorité. Une réservation = **un commit sur `design`** (via PR) **avant** la création du candidat dans Drive ; chaque ligne `reserve` porte une **référence unique** `ref` (ex. `<date>-<aléa>`) ; deux ajouts identiques peuvent fusionner sans conflit Git, donc la **CI refuse tout double `reserve`** d'un même `set_id` ; après fusion, le générateur **vérifie que la ligne `reserve` de ce `set_id` porte bien sa `ref`** avant de créer le candidat (sinon arrêt).
  - Séquence `99` atteinte → **arrêt explicite**, jamais de recyclage. `generer-lot-fonda.js` est migré pour lire ce journal et **s'arrêter** sur tout fichier illisible.

## 7. Page et confirmation de relecture

**GET** (aucune écriture) : par carte, question, réponse attendue, profil avec explication et exemple, toutes les réponses acceptées, `unite`, `arrondi`, `seconde_chance` ; choix « Garder / Écarter » sans défaut ; « Tout rejeter » séparé ; « Essayer une réponse » via le **moteur** du candidat (SRI, CORS). Données via `<script type="application/json">` échappé ; aucun `onclick`. Jeton : `HMAC-SHA256(secret, canonique(["fonda-select/v7", set_id, generation_cle, cle_sha256, empreinte_affichee, moteur.version, moteur.sha256, expire_page, nonce]))`.

## 10. Le filet : portée et sort de chaque détection (C1 v4, C4)

**Ordre** : toutes les détections sont évaluées ; **un seul blocage dur suffit** ; une levée ne neutralise jamais un autre blocage ; le silence n'est jamais une preuve.

**A. Blocages durs propres au lot** (attribuables à ce `set_id`) — **non levables** ; issue : **abandon + nouveau candidat** (§6) :
- sortie `conflit` dans une exécution de ce lot, **quel que soit son statut** ;
- ≥ 2 cœurs distincts, ou cœurs identiques avec `lot_relu` différents ;
- décision de ce lot consignée par une exécution mais **absente de Drive** ;
- fichier de `decisions/` dont le `set_id` interne est ce lot **sans exécution correspondante** ;
- exécution de confirmation de ce lot **`error`/`crashed`/`canceled`**.

**B. Incidents de chaîne** (non attribuables à un lot) — **non levables** ; ils **suspendent toute clôture signée**, pour tous les lots, jusqu'à traitement par Éric ; l'abandon d'un lot **ne les résout pas** :
- exécution de confirmation **non terminée** ou **au statut inconnu** (dont `new`), observée avec et sans filtre — **dont une requête explicite `status=running`** (la liste sans filtre de l'API publique exclut les exécutions actives) —, pagination complète ;
- exécution **sans données exploitables** (lot indéterminable) ;
- fichier **illisible ou non conforme** dans `decisions/` (lot indéterminable) ;
- jeton n8n sans accès aux workflows de relecture.
**Statuts d'un incident (B2)** : `incidents/<id>.json = { id, nature, detecte_le, statut ∈ {"ouvert","resolu"}, resolu_le, preuve_resolution, periode: { debut, fin } }`. **Un incident `ouvert` suspend toute clôture signée** ; l'inscrire ne suffit pas. **Résolution**, selon la nature :
- *jeton sans accès* : accès rétabli **et** observation complète refaite avec succès ;
- *exécution non terminée / statut inconnu* : exécution **terminée ou arrêtée**, puis examinée (statut final, sortie) ;
- *exécution sans données* : examinée ; si son lot reste indéterminable, elle demeure un risque pour **tous** les lots de sa période ;
- *fichier illisible* : examiné puis placé en `quarantaine/` (localisation d'origine conservée).
La **période affectée** va de la première observation possible de la cause (au plus tôt : début de l'exécution, création du fichier ; inconnue ⇒ **depuis le début**) **jusqu'à `resolu_le`**. Tout lot dont la **fenêtre de candidature** — de `cree_le` du candidat **jusqu'à sa clôture technique** (ou jusqu'à maintenant s'il n'est pas clos) — **recouvre** cette période ne peut être clôturé qu'après **abandon et nouveau candidat créé après `resolu_le`**. Période ouverte : `fin = null` (incident non résolu) ; début inconnu : `debut = null` (« depuis toujours »). **Conversion** : si l'investigation attribue l'incident à un lot précis **et** révèle une anomalie relevant de §10.A (conflit, décision disparue, origine inconnue, exécution en erreur…), elle devient un **blocage propre à ce lot** ; une exécution temporairement non terminée, **finalement réussie et rapprochée sans anomalie**, n'est **pas** convertie (l'incident est simplement résolu). Un incident résolu reste listé dans toute attestation ultérieure (`incidents_connus`) ; aucun incident n'est jamais effacé.

**C. Levées — uniquement deux, par Éric, signées, non probantes, confirmation humaine toujours exigée** :
- recherche Drive **`incompleteSearch = true`** persistante → `levees += { type: "recherche_incomplete", constat }` ;
- historique **peut-être purgé** → `levees += { type: "historique_incomplet", constat }`.

**Non bloquant** : plusieurs fichiers de **cœur identique**. **Horloges** : les dates servent à parcourir (fenêtre élargie de 24 h), jamais seules à exclure.

### 11 bis. Formes exactes des sous-objets (v8.2 — 2026-10-15, étape 4.0)

**Notation** (une forme = ce que `canonique.js` sérialise, §1) : `{ a, b }` = objet dont les clés sont **exactement** celles-ci, **dans cet ordre** (ordre des octets canoniques), **toutes présentes** ; `chaîne`, `nombre` (fini), `booléen` ; `X | null` = valeur de type X **ou** `null` (la clé reste présente) ; `[X]` = tableau d'éléments X. Données JSON pures : aucune clé de forme entière, aucune clé `__proto__`. **Dates** : chaîne ISO 8601 UTC à la milliseconde, forme `Date.prototype.toISOString()` (`2026-10-15T09:30:00.000Z`). `canonique.js` vérifie **la forme** (clés, ordre, types, `null`) ; les **valeurs** (énumérations, égalités, formats de date, tris) sont des **invariants** vérifiés par le script de clôture, `publier-lot.js` et la CI (§11, liste ci-dessous).

**Principe pour ce qui vient de n8n** (`provenances`, `execution_cloture`) : forme **minimale et stable**, limitée aux **métadonnées** que l'API publique d'exécutions associe à toute exécution — `id`, `workflowId`, `status`, `startedAt`, `stoppedAt` —, quel que soit le détail du workflow ; rien qui dépende d'un nœud, d'une sortie ou d'un nom de champ interne d'un workflow pas encore écrit. Deux couches distinctes :
- **observation API** (non signée) : accepte des valeurs absentes ou `null` (`startedAt` avant démarrage, `stoppedAt` d'une exécution en cours) — l'adaptateur traite **explicitement** absent et `null`, sans jamais les convertir en date (1970) ni en chaîne `"null"` ; une telle observation alimente le filet (§10 B : exécution non terminée, statut inconnu) ;
- **projection signable** : n'existe que pour une exécution **terminée** ; `statut` doit valoir **exactement** `"success"` et les dates requises être renseignées, **sinon refus explicite** de signer.
Ces métadonnées **ne disent pas à quel lot** une exécution se rapporte : le rattachement à un `set_id` (POST de confirmation de ce lot, clôture de ce lot) est un **rapprochement local** effectué par le script à partir des données d'exécution ; la charge n'en signe que le **résultat** (les métadonnées des exécutions retenues). **Ce contrat de rapprochement est HORS du périmètre figé à l'étape 4.0** : il sera spécifié (sortie métier stable de chaque workflow et règle d'extraction) et relu **au chantier des workflows**. **Tant qu'il n'existe pas, aucune clôture signée n'est possible** (`signer-cloture.js` refuse de signer) ; les formes ci-dessous, elles, n'en dépendent pas. — **Mis à jour** : la saisie locale (§20.6) ne dépend pas de ce contrat et signe depuis le lot 7 ; pour le **parcours page**, le contrat est spécifié au **§21** (r10.7) et la signature page reste refusée jusqu'à P5.

**Observations successives d'une même exécution** : une exécution peut être observée d'abord non terminée (`new`, `waiting`, `running`) puis terminée — **évolution normale**, pas une contradiction. Les observations sont comparées **après normalisation** (dates en UTC milliseconde, `execution_id` en chaîne) ; sont **contradictoires** (→ incident de chaîne, §10 B) : `workflowId` différents, deux `startedAt` **renseignés** différents (un `startedAt` qui passe de `null` à une date est un **enrichissement normal**), deux statuts **terminaux** différents, ou un retour d'un statut terminal à un statut non terminal. La projection signable utilise l'observation **terminale**.

**Dates et tri, normatifs** : une date de source n'est acceptée que si elle respecte la grammaire **ISO 8601 stricte** `AAAA-MM-JJTHH:MM:SS[.fraction]` suivie de `Z` ou d'un décalage `±HH:MM` (aucune autre syntaxe, aucun fuseau implicite) **et** désigne une date calendaire réelle (pas de 30 février, heures 00–23, minutes et secondes 00–59) ; elle est alors convertie en UTC milliseconde (`toISOString()`) **avant** tout tri ou signature. Date hors grammaire, impossible ou sans fuseau → refus (projection signable) ou incident (observation). **Tri lexicographique ECMAScript** (comparaison par unités de code, `<`), **jamais** `localeCompare`. Rappel §10 : une date sert à ordonner et à parcourir, **jamais seule à exclure** une observation.

- **`moteur`** = `{ version: chaîne, sha256: chaîne }` (inchangé).
- **`coeur`** = `{ action, selection, ecartees, empreinte_relue, empreinte_publiee, moteur }` (§1) — chaînes, `[chaîne]`, `[chaîne]`, chaînes, `moteur` ; `selection` et `ecartees` **dans l'ordre des cartes du candidat** (§1), disjoints, sans doublon.

C'est aussi la fin de la **fenêtre de candidature** du §10 B.

## 17. Annexe B — Immuabilité en CI (un seul mécanisme : le tuple)

Script `fonda/scripts/verifier-immuabilite.js` + job **`immuabilite`**.
- **Référence** : sur `pull_request`, `github.event.pull_request.base.sha` ; sur `push`, `github.event.before`. Référence **nulle, introuvable ou historique incomplet → échec explicite** ; jamais de comparaison contre un état vide. Le checkout d'une PR teste le **résultat de fusion simulé**, comparé à la référence.
- **Historique de confiance = chaîne du premier parent** (`git rev-list --first-parent`) de la référence **et** de `design` : les états **réellement publiés** sur la branche. Les commits intermédiaires d'une PR fusionnée (brouillons, révisions avant relecture) n'en font **pas** partie ; son commit de merge, **si**. Parcours sans filtrage par chemin ; objet illisible ou JSON invalide → échec. *(Précision 2026-10-14, suite à l'échec du push post-merge de la PR #8 : sans `--first-parent`, les brouillons du moteur v1 de la PR étaient pris pour des versions publiées.)*
- **Hypothèse du contrat** : intégration à `design`/`main` **par merge commit ou squash uniquement** ; **rebase-merge et push direct exclus** (annexe A, point 4). Un rebase-merge placerait les brouillons d'une PR sur le premier parent ; un fast-forward vers un merge aux parents inversés ferait sortir des états publiés de la chaîne.
- **Continuité** : la référence doit figurer sur la chaîne du premier parent de `HEAD` (PR : le merge simulé a `base.sha` pour premier parent ; push : l'ancien sommet est premier-parent-ancêtre du nouveau) ; sinon **échec explicite**. Détection de clone superficiel impossible → échec.
- **Détecter n'est pas empêcher** : la CI **détecte** une violation (contrôle rouge, au plus tard au push qui avance la branche) ; elle ne l'**empêche** pas. La **prévention** est la **protection de branche** (annexe A).
- **Tuple d'identité d'un lot publié** : `set_id → (empreinte pédagogique, moteur.version, moteur.sha256)`.
- **Registre des tuples** : l'ensemble de **tous les tuples ayant jamais été publiés**, lu dans **l'historique Git de `design`** (autorité) **et** de la référence : catalogue de chaque version + journal des identifiants.
- **Règle unique** — pour chaque entrée du catalogue de la PR :
  - si son `set_id` a **déjà un tuple publié** (sur `design`, sur la référence, ou dans leur historique) → le tuple doit être **identique** (couvre : lot inchangé, **transit `design` → `main`**, remplacement d'attestation à contenu et moteur identiques) ;
  - sinon (première publication) → le journal doit contenir `reserve` puis `publie` pour ce `set_id`, **sans** `abandonne` ni `retire` ; sa présence antérieure en calibration est **autorisée** (**promotion du même candidat réservé**).
  - **Refusé dans tous les cas** : tout changement du tuple ; tout `set_id` dont le journal contient `abandonne` ou `retire` (**jamais réutilisable**, même après retrait) ; tout `set_id` absent du journal.
  - **Retrait** : tout `set_id` présent dans le catalogue de la référence et **absent** de celui de la PR exige, **dans la même PR**, une transition `retire` dans le journal ; sinon refus (empêche un retrait silencieux suivi d'une réintroduction).
- **Règle 0 — M1 (une seule fois)** : si **aucune version** du catalogue dans l'**historique de confiance** (référence et `design`) n'a jamais contenu de champ `moteur` (un catalogue devenu vide ne réarme donc pas la règle), la PR peut ajouter `moteur: v1` aux **8** `set_id` de `HISTORIQUES_FIGES`, à empreintes inchangées, et le tuple ainsi formé devient leur tuple publié ; dès qu'un champ `moteur` a existé dans l'historique de confiance, la règle 0 ne s'applique plus ; le **transit** ultérieur de M1 vers `main` relève de la règle générale (tuple identique).
- **Autres contrôles** : `set_ids-journal.json` en ajout seul, transitions conformes (§6), aucun double `reserve` ; `moteurs.json` en ajout seul ; tout `moteur-correction-v<N>.js` ayant **jamais** existé dans l'historique de confiance est **présent et identique** ; invariant SHA-256 = registre = SRI revérifié.

### 20.5 `lot_relu`, décision et réconciliation
- **`lot_relu-fonda/v1`** = `{ set_id: chaîne, empreinte_complete: chaîne, cartes: [{ item_id: chaîne, choix: chaîne }] }`, `choix ∈ {"garder","ecarter"}` ; `decision-fonda/v1` (§1) devient définie avec ce `lot_relu`.
- **Réconciliation de CHAQUE décision** contre le lot source : `lot_relu.set_id` = `set_id` ; `lot_relu.empreinte_complete` = empreinte complète recalculée ; `item_id` de `lot_relu.cartes` = ceux du lot source, **même ordre**, aucun manquant, doublon ni inconnu ; `coeur.selection` = les `garder`, `coeur.ecartees` = les `ecarter` (ordre du lot source) ; `coeur.empreinte_relue` = empreinte **pédagogique** du lot source (sens v8.2) ; `coeur.empreinte_publiee` = **selon l'action** : empreinte du lot filtré si `action = "accepter"` (vérifiée par la réconciliation) ; empreinte pédagogique du lot **source** si `action = "rejeter"` (convention produite par la saisie locale ; non vérifiée par la réconciliation, exigée en page par `rattachement-page.js`, §21.1) ; `action = "accepter"` ⇒ ≥ 1 carte gardée.
- **Puis unicité** (§10 A, inchangé) : toutes les décisions réconciliées ont le même cœur **et** le même `lot_relu` ; sinon conflit → abandon. La réconciliation **complète** la comparaison entre décisions, elle ne la remplace pas.
- L'**instantané** (§3) contient le **lot source** (sous la clé `candidat_lot`), le cœur, le `lot_relu`, le moteur et le récapitulatif ; il reste écrit **une fois** et vérifié en **octets bruts** (§3.2) — `instantane-fonda/v1` n'a pas de forme canonique (inutile : il n'est jamais reconstruit).
- La **garde maîtresse** de `signer-cloture.js` n'est levée qu'après implémentation et tests de cette réconciliation.

### 20.6 Variante transitoire : saisie locale des décisions (premier lot)
- **Condition** : `relecteur_attribue = "eric"` (mode `auto`) ; Éric ne saisit **jamais** les décisions d'un autre relecteur.
- **Brouillon puis décision figée** : le script local présente chaque carte (rendu humain) et Éric choisit `garder`/`ecarter` carte par carte ; tant que rien n'est écrit, c'est un **brouillon** (corrigeable, rien n'existe). La décision est **figée** quand `decision.json` est écrit (écriture exclusive, hors dépôt et hors Dropbox) avec `nonce` aléatoire, `generation = 0`, `recu_le` = instant de l'écriture, `hash_formulaire = "saisie-locale"`. Une **seconde** décision figée distincte pour ce `set_id` → conflit → **abandon**.
- **Ensuite seulement** : instantané (§3), récapitulatif, code calculé **après** la décision figée, saisie du code, fidélité (§3.4).
- **Fenêtre de candidature locale** = **`[generation.demarree_le, fin_saisie_le]`**, où `fin_saisie_le` = `recu_le` de la décision figée ; elle remplace `[cree_le, clos_le]` pour l'examen des incidents (§10 B) **dans cette variante seulement**.
- **Exceptions explicites**, pour cette variante : pas de page §7 ni de mail de relecture (PRD §12 : dérogation transitoire, la page reste la cible) ; pas de clôture technique ni de révocation de clé (§3.5, §9 (1)) — **`revoque_le` garde son sens v8.2** (premier `clos_le`) et vaut **`null`** dans une charge v2 locale ; pas de workflow de confirmation (`provenances = []`, `execution_cloture = null`).

### 20.7 Listing des observations : un intervalle
- `listing_debut_le` = juste **avant** la première requête de **toute** source observée (API n8n — dont `status=running` et `status=waiting` —, listings Drive) ; `listing_fin_le` = juste **après** la dernière réponse. Les deux sont signés (v2). Ils **documentent** la période d'observation ; ils ne la rendent pas rejouable après purge.
- **Lot généré immuable** (`candidats/<set_id>.lot.json`) **distinct** de l'état de relecture mutable (enveloppe `relecture` du candidat v8.2, parcours page seulement). Pour le **lot généré** : date de modification ≤ `generation.terminee_le` (écrit pendant l'exécution, jamais après) ; lu **avant et après** le listing : empreintes, identifiant et date de modification identiques, sinon **refus temporaire** (relancer la clôture). C'est une **stabilité observée**, pas un verrou.
- Parcours page : l'écriture d'une décision dans `decisions/` est comparée à **`listing_debut_le`** (corrige la limite notée en tête de `signer-cloture.js`).

### 20.8 G3 et G5 : contrats d'entrée
- **G3** : entrées du workflow = `{ set_id, ref }` (motifs stricts) ; le prompt est construit **uniquement** depuis, à la version `referentiel_version`, les champs **`id`, `libelle`, `matiere`, `axe`, `micro_competence`, `enonce_modele`** de la notion et le **palier**, plus les règles de génération du dépôt. **Exclus** : `taux_eval`, `priorite_initiale`, `frequence_base_semaines` et tout autre champ ; aucun cours, mail, donnée de classe ou d'élève. La liste blanche en sortie reste un filet supplémentaire.
- **G5** : modèle **Sonnet** fixé **explicitement** dans le nœud (identifiant épinglé), **sans repli** ; `modele` gravé = champ `model` de la **réponse** ; ∉ liste autorisée épinglée côté signataire → abandon.
- **G5, identifiant épinglé (r8)** : « épinglé » = **snapshot à poids fixes**, jamais un alias flottant. Deux formes recevables : (a) **datée** `claude-sonnet-…-AAAAMMJJ` (format inchangé) ; (b) **sans date**, selon la convention Anthropic `claude-sonnet-<majeure>[-<mineure>]` (ex. `claude-sonnet-5-5`) : la documentation Anthropic ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview), [Model IDs and versioning](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions), vérifiées le 2026-10-21) établit que « *every Claude model ID is a pinned snapshot, including the dateless IDs used from the 4.6 generation on* » et que « *dateless IDs are their own pinned snapshot* » ; chaque mise à jour du modèle reçoit un nouvel identifiant. **Principe** : la **vraie épingle** est la liste curée `fonda/data/modeles-autorises.json` (snapshots épinglés uniquement, renseignée sur preuve d'une sonde §20.8 : identifiant d'exécution et date), et le signataire grave le champ `model` de la **réponse**, toujours un snapshot épinglé. La règle de forme (`modeleEpingle`, `fonda/scripts/attestation-signee.js`) n'est qu'un **garde-fou** contre une liste mal remplie : aucun seuil de version n'y est encodé (fragile) ; les **alias sans date antérieurs à la 4.6** (pointeurs vers un identifiant daté : `claude-sonnet-4-0`, `claude-sonnet-4-5`, etc.) y sont refusés par une **liste noire explicite** (`ALIAS_PRE_46`), à compléter si Anthropic en documente d'autres.

### 20.10 Exécution purgée, réglages de l'instance
- Exécution de génération introuvable, purgée ou sans données → **refus** (abandon si elle ne reviendra pas). `historique_incomplet` (§10 C) ne vaut **que** pour l'incertitude d'**exhaustivité** du listing, **jamais** pour masquer une source obligatoire absente ni une anomalie constatée.
- **Condition d'activation** (§13) : sauvegarde des données des exécutions réussies **et** en erreur activée, purge automatique **désactivée**, vérifiées et consignées avant la première génération réelle.

### 20.11 Publication, reprise, promotion
- **`publier-lot.js`** : **précondition** — aucune modification non commitée sur `catalogue-fonda.json` et `set_ids-journal.json`, et aucun fichier `lots/<set_id>.json` existant (sinon refus avant tout calcul, ce qui préserve les modifications préexistantes) ; tous les contrôles **avant** toute écriture ; puis écrit le lot (création exclusive), l'entrée du catalogue **et** la transition `publie` du journal (`ref` de transition = `ref` de réservation + `":publie"`). Ce n'est **pas** une transaction atomique.
- **Reprise contrôlée** après une panne partielle : `publier-lot.js --reprendre` est **exempté des préconditions ordinaires** (qui interdisent précisément l'état laissé par la panne), mais **seulement** si les trois fichiers sont dans un **état intermédiaire attendu**, calculé depuis le **`HEAD` du premier lancement** : au premier lancement, `publier-lot.js` consigne le **SHA de `HEAD`** dans un marqueur local non suivi (`.git/fonda-publication-<set_id>`, hors arbre de travail) ; `--reprendre` exige ce marqueur et **`HEAD` = SHA consigné** (tout commit intervenu entre-temps, même sur d'autres fichiers → refus), puis vérifie :
  - `lots/<set_id>.json` : absent, ou **non suivi** et **identique octet pour octet** au lot à publier ;
  - `catalogue-fonda.json` : identique à `HEAD`, ou identique à `HEAD` **plus exactement** l'entrée attendue ;
  - `set_ids-journal.json` : identique à `HEAD`, ou identique à `HEAD` **plus exactement** la ligne `publie` attendue ;
  - aucune autre modification sur ces chemins.
  Si c'est le cas, il **complète** les écritures manquantes (aucune restauration, rien d'autre n'est touché) ; **sinon refus AVANT toute écriture**, traitement manuel par Éric. Aucune PR n'est ouverte sur un état partiel.
- **Longueur des `ref`** : une `ref` de **réservation** fait **au plus 120 caractères** (la transition `":publie"` reste sous la limite de 128 de `journal-set-ids.js`) ; le générateur et la CI le vérifient.
- **Promotion d'un lot de calibration** (`_01`) : **hors brique 1**. Un lot de calibration n'a pas d'exécution de génération conservée ; il ne peut pas satisfaire la liaison v2 et **aucune provenance n'est fabriquée**. Sa promotion exigera un contrat propre (ultérieur). Règle générale déjà valable : un `set_id` n'est jamais à la fois en calibration et au catalogue ; le retrait du fichier de calibration est un geste validé par Éric (`--promouvoir`).

### 20.12 Référentiel archivé, jamais courant
- Résolveur commun (signataire, publication, CI) : sommet de confiance fixé (pour la CI : la référence du contrôle, §17), parcours **premier parent** de `design`, recherche d'une version de `fonda/data/referentiel.json` dont `"sha256:" + SHA-256(octets)` = `referentiel_version` ; introuvable ou illisible → refus. Le relecteur attribué d'une attestation est vérifié contre **cette** version ; une **réattribution ultérieure n'invalide jamais** une attestation passée. `publier-lot.js` et `catalogue.test.js` cessent d'utiliser le référentiel courant pour ce contrôle.

**Rapprochement exécutions ↔ fichiers de décision — symétrique sur le tuple (lot, nonce, id Drive, empreinte)** (finding 5) :
- Ensemble **X** = tuples des résultats `decision` du lot ; ensemble **F** = pour chaque fichier de `decisions/` du lot, `(set_id interne, nonce interne, id Drive, "sha256:" + SHA-256(octets canoniques du contenu lu))`, avec `nom = <set_id>-<nonce>.json` et `properties.fonda_set_id`/`fonda_nonce` égaux au contenu (sinon **abandon**).
- **Complétude préalable (§20.13)** : un constat **négatif** (« absent », « non désigné ») n'est établi que sur une observation **complète** de ce dont il dépend ; sinon **refus temporaire** (observation incomplète), jamais un abandon. Une **substitution observée** (fichier présent, empreinte ou identifiant différent) reste un **abandon** quelle que soit la complétude.
- **R1** chaque tuple de X a **le même tuple COMPLET** dans F : même **lot**, même **nonce**, même **id Drive** et même **empreinte** (le nonce et le lot sont comparés **explicitement**, jamais déduits de la seule cohérence de la sortie du workflow). L'identité physique (id Drive) est recherchée parmi **tous** les fichiers lus, **avant** tout filtrage par lot : un id consigné qui porte une autre décision (autre nonce, autre lot, autre empreinte) est une **substitution observée** → **abandon**, quelle que soit la complétude. Fichier présent mais différent → **abandon** (substitution observée). Fichier **absent** → **abandon** seulement si l'absence est **établie** : listing de `decisions/` **complet** (lu sans échec **et** sans `incompleteSearch`). **Une levée `recherche_incomplete` ne rend jamais un listing complet** : elle autorise seulement à poursuivre malgré une incertitude d'exhaustivité (§10 C) ; une pièce obligatoire **manquante** dans un listing incomplet, levé ou non, donne un **refus temporaire**. L'abandon exige une absence **établie** ou une substitution **observée**.
- **R2** chaque fichier de F est **désigné** par au moins un tuple de X **sur le tuple COMPLET** (lot, nonce, id Drive, empreinte) — ni par le seul id, ni par le seul nonce. Fichier non désigné → **abandon** (fichier sans exécution propre, §10 A) **seulement si** l'examen des exécutions de confirmation est **complet** (listing sans échec et **aucun** détail `indisponible`) ; sinon **refus temporaire**. Un **doublon physique** (deux fichiers, même nom ou même nonce) dont un seul est désigné → **abandon**.
- **R3** plusieurs tuples de X pour un même nonce (resoumission de la **même** page) : admis **seulement** s'ils sont **identiques** (même id Drive, même empreinte), au plus un `creee`, les autres `existante` ; sinon **abandon**.
- **R4** un nonce par affichage (21.5) : deux nonces → deux fichiers → **unicité du cœur et du `lot_relu`** (§10 A, §20.5) tranche.
- **R5** `conflit` ou `erreur` du lot (quel que soit le statut) → **abandon**.
- **R6** `generation` : résultat `decision` = `decision.generation` du fichier = `candidat.relecture.generation_cle` ; sinon **abandon** (clé révoquée, autre émission). La comparaison **exécution ↔ fichier** est faite **directement**, même si le candidat est indisponible.
- Seules des exécutions `existante` observées (le `creee` purgé) : admis si R1–R6 tiennent ; c'est la limite d'exhaustivité du §0 (le silence ne prouve rien), pas une preuve.

**Clôture ↔ candidat lu** (finding 8) : `drive.lireCandidat(setId)` renvoie l'**enveloppe** `candidat-fonda/v1` avec son identité Drive dans le champ `.drive` (contrat 21.8) ; pour la clôture retenue (§9 (1)) — `derniere` = l'observation **fusionnée** (21.2, fusion) de cette exécution : `sortie.candidat_fichier_id` = **`candidatEnv.v.drive.id`** ; `sortie.clos_le` = **`candidatEnv.v.relecture.clos_le`** ; toute clôture réussie du lot porte ce **même** `clos_le` (premier passage, jamais réécrit) et le même `candidat_fichier_id` ; sinon **abandon** — vérifié sur **chaque** clôture observée du lot, indépendamment de l'exhaustivité. La clôture « la plus récente » n'est **retenue** que sur une sélection **prouvée** (listing complet, aucun détail indisponible) ; sinon refus temporaire, et aucun contrôle propre à la « dernière » n'est appliqué. **`nb_decisions_listees` est un diagnostic seulement** (renvoyé par `evaluerPage` avec le décompte du signataire, affiché par le CLI page en P5 ; jamais comparé pour décider) : l'état historique de `decisions/` n'est pas reconstructible par `modifie_le`. Les décisions sont jugées sur ce que le signataire **observe** : (a) **instabilité** — fichier du lot dont `modifie_le` > `terminee_le` de la clôture retenue ou > `listing_debut_le` → **nouvelle clôture technique requise** (refus temporaire, règle existante §20.7) ; une décision écrite avant la fin de la clôture mais absente de son listing reste **évaluée** (réconciliation, unicité, récapitulatif) ; (b) **disparition ou substitution ÉTABLIE** — tuple consigné par une exécution absent de `decisions/` ou d'empreinte différente (R1), fichier non désigné (R2) → **abandon** ; (c) **`incomplete_search`** (clôture ou signataire) → **§10 C** : refus temporaire sans levée `recherche_incomplete`, jamais un abandon.

### 21.3 Lecture des détails : pré-lecture pendant le listing borné ; observation des exécutions en vol

**Tranché** : les détails avec données (`api.lireExecution(id)`) de **toutes** les exécutions **terminales** observées des workflows de confirmation et de clôture sont lus **dans** `[listing_debut_le, listing_fin_le]`, rangés dans des tables `id → brute | INDISPONIBLE | null` attachées aux observations (`clotures.details`, `confirmations.details`) par `adaptateurs-page.js` (`preLireDetails`), puis lues par `evaluerPage`, qui reste **pure et synchrone** (corps délégué à `rattachement-page.js`, patch figé 21.8). Raisons : (1) toutes les lectures dans l'intervalle signé (§20.7) ; (2) même mécanisme que la génération, déjà testé ; (3) aucune panne réseau mêlée à l'évaluation ; (4) coût inévitable (sans détail, le lot d'une exécution est inconnu). Conséquence : `rattachement(brute)` reçoit l'exécution **avec** données ; la **garde maîtresse** et le poison de saisie locale sont **inchangés**.

**Exécutions en vol (correctif préalable, finding 3, hors r10)** : l'API publique de n8n 2.6.3 **exclut** les exécutions actives de la liste sans filtre, sauf demande explicite `status=running`. `observer()` interroge bien `running`, `waiting` puis la liste complète, mais l'adaptateur de production ne transmettait pas `status` au serveur. **Correctif séparé, fusionné avant P1** : `status` passé au serveur, résultat non refiltré, fusion des trois listes par `observer()` ; test fidèle à la sémantique n8n.

### 21.4 Déni de service et exécutions sans données (finding 4)

- **Pas de promesse de limitation à un lot.** Peuvent produire un **incident de chaîne** (suspension de toutes les clôtures, §10 B) : une exécution `crashed` sans `runData` ; un arrêt au **timeout** (120 s) sans entrée exploitable ; une exécution encore en vol à l'observation ; un détail purgé. **Risque global assumé** : le signataire **refuse de signer** tant qu'une écriture reste possible ; une exécution sans données n'est **jamais ignorée**.
- **Abandon d'un lot choisi par un tiers** : une exécution en erreur dont l'entrée porte un `lot` valide (non prouvé par C2) est attribuée à ce lot → **abandon** de ce lot (fail-closed). Assumé et documenté.
- **Réduction** (sans en faire une garantie) : rejet en `success` (E10), nœud d'entrée trivial, bornes de taille avant l'exécution.
- **À prouver sur copie (§13) avant activation** : corps malformé, corps hors taille (`N8N_PAYLOAD_SIZE_MAX`), arrêt avant le nœud d'entrée, timeout ; pour chacun : statut observé, présence de `runData`, résultat de `rattacherPage`. Le **coût** du listing croît avec les rejets conservés (rétention §20.10) ; relevé lors de la recette.

### 21.5 Cycle du candidat (`candidat-fonda/v1`)

- **Fichiers** (`FONDA-Lots`) : lot source **immuable** `candidats/<set_id>.lot.json` (§20.4) **distinct** de l'enveloppe **mutable** `relecture/<set_id>.candidat.json` = `{ schema: "candidat-fonda/v1", lot, relecture }` ; `lot` = copie du lot source (`empreinte_complete` égale, vérifiée à l'émission et à la clôture).
- **`relecture`** = `{ statut, generation_cle, cle_sha256, cree_le, expire_le, clos_le, relecteur_attribue, referentiel_version, moteur: { version, sha256 }, envois }` ; `envois = [{ generation_cle, envoye_a, le }]`.
- **Émission** : pré-conditions = réservation au journal, exécution de génération retenue (§20.2), lot source lu, **aucune** enveloppe existante ; `k` = 32 octets aléatoires (Crypto **v1** « Generate », hex 64), **seul `cle_sha256` stocké** ; `generation_cle = 1` ; `cree_le` ; `expire_le = cree_le + 14 j` ; `clos_le = null` ; `referentiel_version` et `moteur` = ceux de la **sortie de génération** ; **`relecteur_attribue` = relecteur de la notion dans le référentiel ARCHIVÉ à `referentiel_version`** (§20.12 ; ce champ n'est pas dans `generation-fonda/v1`) ; mail au relecteur (adresse **dans n8n**, jamais dans le dépôt), lien `…/fonda-select?lot=<set_id>&k=<k>` ; `envois += { generation_cle: 1, envoye_a, le }`.
- **Réémission** (`statut = en_attente`) **seulement si aucune décision du lot n'existe dans `decisions/`** : nouvelle `k`, `generation_cle += 1`, nouveau `cle_sha256`, `expire_le` repoussé. **Sinon** : pas de réémission ; abandon et **nouveau `set_id`**, relecture entièrement refaite (§6) — les décisions existantes ne sont **jamais** effacées.
- **Clôture technique** : `statut → clos`, `clos_le` écrit **une fois** ; ensuite C3 refuse (410).
- **États à la clôture signée** : `en_attente` (avec `clos_le = null`, normal avant la clôture technique) → **refus temporaire** ; `abandonne` → **abandon** (définitif) ; statut inconnu → **incident**.
- **Abandon** : `statut → abandonne` (§6).
- **Exposition de `k`** (assumée, §0) : `k` transite dans le mail, l'URL et les **données d'exécution** n8n (conservées par l'instance). Le signataire lit les détails de **tous** les lots : il peut y rencontrer la `k` encore active d'un **autre** lot. Promesse **limitée aux traces du signataire** : `rattacherPage` n'extrait que les champs de 21.1 ; `k` n'apparaît dans aucune sortie, journal, fichier ni affichage du signataire. Seule la clé **du lot clôturé** est morte à la clôture.
- **Intérim** : non applicable au parcours page (§20.16 : saisie locale seule).

### 21.6 Page carte par carte (§7 précisé)

- **GET** `/fonda-select?lot&k` : C3 ; sinon page d'erreur sans donnée du lot. **Aucune écriture.**

- **Serveur (C1, C5)** : champs **exactement** `lot, k, generation, empreinte, moteur_version, moteur_sha256, expire_page, nonce, jeton, action` + **un** `choix_<item_id>` ∈ {`garder`,`ecarter`} **pour chaque carte** (`action = "accepter"`), **ou** `confirmer_rejet=oui` sans aucun `choix_` (`action = "rejeter"`) ; `selection`/`ecartees` construits côté serveur dans l'ordre du candidat (§1).
